## 做了什么

| 项 | 实现 |
|---|---|
| 邀请码必填 | 邀请制下必填，全空白也算未填，提示“邀请制下必须填写邀请码”；后端返回 `invite_code invalid` 时回显到字段上 |
| 申请说明必填 | 邀请制下必填（0/200 计数），全空白也算未填 |
| 蜜罐 `website` | `<div class="reg-hp" aria-hidden="true">` 内放 `<input name="website" type="text" tabIndex=-1 autoComplete="off">`；用 `.reg-hp` 移到可视区外（不用 display:none，避免机器人识别后跳过）。对用户不可见，读屏器读不到，Tab 键也不会停在上面。提交时取它的实际值，用户正常操作时为 `''`。即使被填了也照样提交，由服务端判定；界面显示和正常提交一样的“已提交待审核”，不提示命中 |
| `form_started_at` | 注册表单子组件挂载时用 `useState(() => serverNowMs())` 记一次（毫秒整数），提交时一并带上 |
| 服务器时钟校正 | 新增 `lib/serverClock.ts`：`GET /meta/registration` 响应后读 `Date` 头，offset = Date − 本地接收时刻。`Date` 头精确到秒且晚于服务端生成时刻，所以这个 offset 是下界，算出的时间只会偏早不会偏晚，正常用户不会被误判为“太快”。没有 Date 头或解析失败时 offset = 0。`api/client.ts` 的 `RequestOptions` 增加 `onResponse` 回调 |
| 类型 | `RegisterRequest` 增加 `website: string \| null` 和 `form_started_at: number \| null` |

## Mock（MSW，按 v0.2.8 #11）

- `/meta/registration` 返回 `Date` 头。
- `/auth/register`：
  - 出现未知字段时返回 400 `extra_forbidden`（`agreements` 照旧忽略）；`form_started_at` 不是整数时返回 400 `invalid`。
  - 检查顺序：关闭 → 503，然后 400 校验，然后 409 重名，然后蜜罐。
  - 命中条件：`website` 去掉首尾空白后非空，或 now − form_started_at < 3000 ms（未来时间也算命中）。
  - 命中时返回同样的 201（id 随机），不建用户、不消耗邀请码，并在 `state.honeypotHits` 里记录 `website` / `too_fast` / `both`，对应审计 `auth.register_honeypot {trigger}`。
- mock 不做限速和 pending 上限，后端有。

## 遗留问题

1. 蜜罐依据的是契约 v0.2.8 #11，而前端整体仍按 v0.2.7。v0.2.8 其余内容是否同步，等用户决定。
2. 前端只能拿到秒级 Date 头，offset 可能偏早最多约 1 秒加网络单程时间，只影响“太快”判定的宽松程度，不会误判。如果后端将来提供毫秒级服务器时间，可以替换。
3. 注册页还没加载完 `/meta/registration` 时不会渲染表单，所以 `form_started_at` 总是在校正之后才取。如果 meta 请求失败，页面停在错误态，不会用未校正的时间提交。
4. 后端在校验阶段先占用邀请码再查重名；mock 只是先查 409 再查蜜罐，两者的顺序差异对前端没有可见影响。
