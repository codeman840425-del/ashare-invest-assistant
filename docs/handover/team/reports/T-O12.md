## 1. 调研结论（复核）

自 07b8d74 草稿以来，importing/keys.py、storage.py 只有 6670b10 改过（主密钥按服务分配：只有 api/worker 持有，ingest 持有即拒绝启动）。加密格式没变：
- 交割单加密用的是 **APP_MASTER_KEY**。DATA_LICENCE_SEAL 是麦蕊证书用的另一套 HPKE 密钥，带 seal_key_version，已支持多版本，与本单无关。
- `derive = HMAC-SHA256(APP_MASTER_KEY, label)`：
  - `aia/imports/kek/v1` → KEK，用来包裹每个文件的 DEK。文件格式 `AIA1|nonce_k|wrapped_dek(48)|nonce_d|ct`，AAD=batch_id，存放在 `<卷前缀>_imports` 卷。
  - `aia/imports/rawline/v1` → `import_rows.raw_line`，格式 `"v1:"+b64(nonce+ct)`。
  - `aia/imports/holder/v1` → `shareholder_code_hmac`（**明文不入库**）。
- **没有密钥编号**（AIA1、v1 都只是格式版本），**只能用一把钥匙解密**，也没有重加密任务。

### 换主密钥会影响什么

| 依赖 | 换钥后 | 能不能迁移 |
|---|---|---|
| 导入文件（KEK 包 DEK） | 解不开 | 能：拿旧 KEK 解出 DEK，再用新 KEK 包一次（只动 48 字节，不用重加密正文） |
| import_rows.raw_line | 解不开 | 能：旧钥解、新钥加，分批做 |
| shareholder_code_hmac | 对不上（去重、关联失效） | **不能重算**（没有明文）→ 旧钥只能留着做比对 |
| invite_codes.code_hash | 未使用的邀请码全部失效 | 不能重算 → 双钥比对，或让旧码自然过期 |
| licence_hmac（HKDF data-licence-dedup-v1，有唯一约束） | 证书去重失效，同一证书可能被录两次 | 不能重算 → 过渡期新旧两把都算一遍再查 |
| 冷却指纹（data-licence-cooldown-fp-v1） | 冷却期判断失效 | 不能重算 → 过渡期两把都算 |
| login_attempts / audit_logs.ip_hash | 新旧记录对不上（限速、审计关联断开） | 不能重算 → 按保留期自然淘汰 |
| 分页游标签名 | 旧游标失效 | 无需迁移（短期，客户端重取） |
| llm_providers.api_key_ciphertext | 解不开 | 有 key_version 列，但代码还没实现 |

**结论：V1 没法做无损轮换。** 现在换主密钥会让导入文件、raw_line 解不开，并让所有 HMAC 类数据失效，后端也没有任何多钥支持。按裁定 ⑤，V1 只保证主密钥**不丢、能识别、能放回原位**（§3），并把轮换前提登记给后端（§2）。

## 2. 轮换方案（V2，需要后端实现、架构师定排期）

1. **密钥编号（m8）**：`kek_id = HMAC-SHA256(KEK, "aia/imports/kek-id/v1")[:8]`，单向，不泄露 KEK。
   - 新文件格式 `AIA2|kek_id(8)|nonce_k|wrapped_dek|nonce_d|ct`；raw_line 格式 `v2:<kek_id_hex>:<b64>`。
   - 读取时 AIA1 和 v1 按“旧格式、当前钥”处理。
2. **多钥配置**：secret 改为 `app_master_keys`（JSON：`{"<id>": "<key>"}`），加上环境变量 `APP_MASTER_KEY_ID`（当前用于加密的那把）。
   - 解密按 kek_id 选钥；HMAC 类查询在过渡期对**所有在用的钥**都算一遍（新旧两把）。
   - 写入只用当前钥。
   - secret-env.sh、app-master-key-ensure.sh 要跟着改，这部分是运维的活。
3. **轮换步骤**：
   1. 备份（§3 脚本 + db-backup + 导入卷）。
   2. 往 `app_master_keys` 里加新钥，重建 api/worker（这时还不切换）。
   3. 把 `APP_MASTER_KEY_ID` 切到新钥，重建。
   4. 跑后台重包任务（worker）：文件只重包 DEK，raw_line 分批重加密，llm 密文按 key_version 迁移。
   5. 核对：旧 kek_id 计数 = 0，抽样解密都通过。
   6. 旧钥降为“只用于比对”：HMAC 列没有明文，旧钥要一直留着做比对，直到相关数据按保留期淘汰或被用户重新录入（比如<account-field>在下次导入时重算）。
   7. 更新离线备份，旧钥备份按保留策略处理。
4. **泄露应急（V1 现状）**：主密钥泄露时没有无损手段。只能二选一：
   - (a) 继续用：限制访问面，补审计；
   - (b) 破坏性重置：换新钥，导入文件、raw_line 作废需重新导入，邀请码重发，证书去重和冷却重置。

   这由产品负责人决定，运维按 §3 先备份再执行。

## 3. 运维交付（本次）

`deploy/scripts/app-master-key-backup.sh`：

| 子命令 | 作用 |
|---|---|
| `fingerprint [--src F]` | sha256（与 runbook database.md §4 的手工口径一致） |
| `backup --dest DIR [--src F]` | 生成 `app_master_key-<UTC>.key`（600）+ `.sha256`。拷贝后核对摘要；用 ln 落盘，不覆盖已有文件 |
| `verify BACKUP [--src F]` | 一致返回 0，不一致返回 1，备份与 .sha256 不符返回 4 |
| `restore BACKUP --dir DIR` | 目标已存在就拒绝（**从不覆盖**）。先核对 .sha256，600，属主 10001 |
| `drill` | 用假密钥在临时目录走一遍全流程，结束就删 |

- 安全约束：第一条语句关掉 xtrace；密钥不经命令行参数或环境变量传递，不打印，只输出路径和 sha256；只在读不到文件时才用 `sudo -n cat`，而且输出只进管道。备份目录必须是仓库外的绝对路径，不能是密钥目录本身，里面有 `*.dump` 时拒绝（主密钥不能和库备份放在一起）。长度小于 32 字节的源文件拒绝。
- 没有 `rotate` 子命令（V1 不轮换，调用会返回 2）。
- 测试：scripts/ci/tests/test_app_master_key_backup.py，12 个用例，全部用假密钥、临时目录。覆盖指纹口径、往返、bash -x 不泄露、不覆盖、错钥和损坏检测、4 种不合法备份目录、短文件和缺失文件、未知子命令、drill。
- runbook：deploy/runbooks/database.md §4 加了一段脚本用法。
