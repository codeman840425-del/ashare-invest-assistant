## 2. 上游停机演练（aia-t01，19:39–19:40）

做法：只停、启 `api` 一个服务（compose stop/start），**全程不碰 nginx**。探针每 0.1 s 请求一次 `GET /api/v1/health/live`（curl 超时 3 s）；同时在 nginx 网络命名空间里抓包（只抓新建 TCP SYN 和 UDP 包头，不抓载荷），并在停机前、停机中、恢复后各取一次 conntrack 和 ss 快照。

### 2.1 时间线

| 时间 | 事件 |
|---|---|
| 19:39:35.28 | 最后一个停机前 200 |
| 19:39:38.281 → .860 | `stop api` 开始 → 完成 |
| 19:39:38.692 | 第一个 502（api 正在退出，连接被拒） |
| 19:39:38.808 → ~19:39:48.1 | **挂起窗口**：3 次探针都超时（000）。原因见 §2.3 |
| 19:39:48.145 | 开始稳定返回 502（解析失败，立刻返回） |
| 19:40:25.3 | nginx 被判为 unhealthy（停机约 47 s 后，健康检查连续 5 次失败） |
| 19:40:27.575 → 19:40:31.268 | `start api` 开始 → 完成 |
| 19:40:33.105 | 恢复 200（api 启动完成后 1.8 s；不超过 `valid=10s`） |
| 19:40:35.3 | nginx 恢复 healthy（start 后约 4 s） |

探针统计：200×79、502×408、000（超时）×3。
**出错窗口共约 54.4 s**（19:39:38.69 → 19:40:33.10）：其中约 44.9 s 是立刻返回的 502，约 9.3 s 是请求挂起。api 实际停了约 52.4 s（38.86 → 31.27）。

### 2.2 nginx 没有重启

| | 停机前 | 恢复后 |
|---|---|---|
| 容器 ID | a15a77da890b | a15a77da890b |
| RestartCount | 0 | 0 |
| State.StartedAt | 2026-11-02T02:24:06.326Z（= 19:24:06 MST） | 同左 |

结论：**api 停机时 nginx 变成 unhealthy，api 恢复后 nginx 自己恢复 healthy，全程没有重启。** ✅

### 2.3 发现：缓存窗口内请求会挂起（建议加 proxy_connect_timeout）

api 停下后的约 10 s 里（`valid=10s` 缓存还没过期），nginx 继续向旧 IP <host>:8000 发 SYN。容器已经不在，对方没有 RST，ss 能看到 SYN-SENT。因为没设 `proxy_connect_timeout`，这时进来的请求最长会挂 60 s（探针 3 s 就超时了，所以是 000）。缓存过期后改走"解析失败 → 立刻 502"。
**建议**（待架构师定，本次没改）：在 nginx 的 /api/ 相关 location 里加 `proxy_connect_timeout 3s;`（2–5 s 都行），把这个窗口里的请求变成很快返回 502/504。顺便还能缩短 nginx 被判 unhealthy 的时间。

### 2.4 未知名字解析（停机期间，在 nginx 容器里 `nslookup <名字> <host>`）

| 名字 | 结果 | 耗时 |
|---|---|---|
| aia-no-such-host-o13 | SERVFAIL，没有地址 | 0.057 s |
| aia-no-such-host-o13.example.com | SERVFAIL，没有地址 | 0.057 s |
| api（停机中） | SERVFAIL，没有地址 | 0.051 s |

结论：**未知名字在 1 s 内解析失败**（约 0.06 s），也没有解析到外部地址。✅（gateway 日志里对应 `could not be resolved`。）

### 2.5 停机期间有没有对外连接（只记目标 IP 和端口）

- **tcpdump**（nginx netns，`-i any`，新建 SYN 和 UDP，只抓包头，共 1867 个包）：目标 IP 只有
  - <host>（Docker 嵌入式 DNS）
  - <host>:53（嵌入式 DNS 往 `dns: <host>` 转发，共 413 个包，在 netns 里被拒，没有出宿主）
  - <host>:8000（api；停机后的 SYN 都是 §2.3 那批）
  - <host>:80（nginx 自己，入站流量，来源 <host> = 探针经过的端口映射）
  - **发往任何非回环地址 53 端口的包：0 个。**
- **conntrack**（/proc/net/nf_conntrack，nginx netns 里取；停机前 24 条、停机中 686 条、恢复后 762 条）：目标地址都在 <host>/8 或 <host>/16，**没有一条指向外部。**
- **ss**（停机中）：只看到连 <host>:8000 的 SYN-SENT，没有对外连接。

结论：**停机期间没有对外连接，也没有对外 DNS 查询。** ✅（2a9d141 时的风险是：宿主 DNS 的 fakeip <host> 会把请求带到外部代理。d1a148f 加了 `dns: <host>` 后已消除，这次实测也证实了。）

### 2.6 其他

- 演练结束后 aia-t01 全部服务 healthy，/healthz、/api/v1/health/live、/api/v1/health/ready、/meta 都返回 200。没有动业务数据，也没有重启机器。

## 5. CI 跟进（架构师对 d1a148f 的评审：m1 / m2 / n）

`scripts/ci/check_gateway_limits.py` 和 `scripts/ci/tests/test_gateway_limits.py`：

- **m1**：`resolver` 的地址列表必须正好是 `<host>` 这一个。`<host> <host>` 这类多地址写法，或者其他地址，一律拒绝（反例测试已加）。`map $host $aia_api_upstream` 的每个分支都只能是内部短名（`名字:端口`），不能写外部地址或 URL。
- **m2**：任何 compose 文件里都不能给 nginx 设 `network_mode`（包括 `host`）。nginx 用 `extends` 也拒绝。
- **n**：自定义 YAML 标签（`!reset`、`!override` 等）不再让检查崩溃，而是明确报"不允许"，CLI 返回码正常。override 文件也纳入检查：deploy/compose/ 下除了 base 和 dev 之外的 compose 文件，一出现就报错；所有 compose 文件都要过 network_mode 和 extends 检查；非 base 文件不能覆盖 nginx 的 healthcheck 和 dns。
- 结果：真实仓库 0 个问题；gateway 用例 82 passed；全量 selftest 506 passed / 55 skipped。
