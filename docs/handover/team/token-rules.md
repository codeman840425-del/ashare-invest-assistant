# 全组 token 规则（2026-11-07 起执行）
依据：reports/token-audit/*.md 六份自查加编排者自查。占比都是主观估计，不是计费数据。

## 浪费在哪
1. 汇报和转述重复：同一件事分别发给用户、编排者、架构师；各方长篇复述；发确认消息；中英混杂。各角色估计占 30–45%。
2. 全量重跑：每个提交都跑干净检出的全量 CI、vitest 和测试；同一个 HEAD 重复跑；整套结果反复回传。占 20–50%。
3. 零散插单：每次插单都重写权限、背景和模板，执行中被打断后要重读上下文。占 20–35%。
4. 裁定多轮返工：T-R12c～i 共 7 轮，问题没有一次问齐、一次写全，其中有的是更正自己的错误。占 30–50%。
5. 编排者自身：逐条中转裁定、派单时附整段背景、给用户发多条进度。

## 规则
1. 消息只写四项：任务号、结果、hash、需要谁做什么。细节只写在 reports/，报告不超过 20 行，原始日志单独存文件。不发确认、回执、复述，一律用中文。
2. 用户只由编排者对接。其他角色不给用户发消息，内部迭代也不发。编排者只在一批完成、需要用户决策或遇到阻塞时给用户发一次。
3. 固定约束（权限边界、扫描要求、不推送、密钥纪律）写在 team/rules/ 和任务单里，派单只引用路径，只写新增的差异。
4. 插单先进 status/<角色>.md 的队列，当前项提交后再取。只有安全阻塞可以立即插队。每完成一项就提交并写报告，中断后读报告恢复，不重读全部上下文。
5. 测试分层：中间提交只跑受影响的用例、typecheck 和暂存区扫描；一批结束后在最终 HEAD 上跑一次干净全量。基线没变就不重复跑。截图只在页面有可见变化时拍。
6. 评审只看 diff 加相关 grep，只跑相关用例。分段评审，每段 5–8 个提交，评完一段就给推送点。
7. 裁定：同一主题的问题攒齐后一次提出。裁定前先 grep plan 里的定义，一次写全适用范围、取值和例外。研究员和后端先自查一致性再提问。
8. 一个裁定只写一份报告，消息里只给路径，不分别向四方复述。
9. 不变的安全底线：密钥扫描、权限负例、部署前征得同意、证书纪律，都不能为了省 token 而削减。
