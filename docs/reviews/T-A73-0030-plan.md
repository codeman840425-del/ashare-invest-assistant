## 1. M6（扩展）问题核实（已复现）

T-A72 的 M6 只写了「scope 孤儿、CLI 删不到」，实际更严重：CLI 在 0029 库上的前置检查就会失败，dry-run 和 `--execute` 都一样。三个独立的失败点：

1. **regclass 解析报错**：CLI:820 调 `_user_object_ids`，它对每张「有指向 app.users 外键」的表做 `CAST(:t AS regclass)`（CLI:720）。外键发现查询（CLI:700-704）不过滤 schema，会找到 `ingest_private.mairui_gate_bindings.user_id`（0029:21）。aia_maint 对 `ingest_private` 没有 USAGE（T-O57，grants:155、179-181），已复现 `ERROR: permission denied for schema ingest_private`，整个 CLI 中止。
2. **漂移守卫计数报错**：即使跳过第 1 点，CLI:849 的 `_unhandled_fk_refs`（CLI:605-622）会把该列判为未覆盖的外键（不在 `HANDLED_FK`，CLI:364-365），并以 aia_maint 身份 `count(*)`（CLI:583），已复现同样的 permission denied。
3. **触发器白名单拒绝**：0029 在 `app.user_data_licences` 上建了 `mairui_gate_on_licence_deletion`（0029:69-72）。这张表在 CLI 的触发器自检范围内（CLI:333、550-552），该触发器不在 `TRIGGER_ALLOWLIST`（CLI:437 起），所以 CLI:850 会列出它，`--execute` 拒绝执行（CLI:1194-1196、1219-1220）。

另外，已复现：aia_maint 删除证书行时，0029 触发器（SECURITY DEFINER）会删掉绑定行并把 scope 置为 detached，但 scope 行**留下**，`origin_licence_id` 仍是已删证书的 id。CLI 对其他保留表的口径是把证书行 id 清掉（`ops.data_licence_events` 置 NULL，CLI:142；detail 去掉含证书行 id 的项，CLI:29-33），scope 行不符合这一口径。

## 2. M6 设计

### 2.1 接口与契约变化

- HTTP 接口：**无**。
- 契约：只在 `docs/api-contract.md` §7.11.2 T-A52 第 9 条「grants 口径」下补一条，标「草案（0030）」：aia_maint 只多获授两个 `ops` 函数的 EXECUTE，仍然不得获授 `ingest_private` 的任何权限。

### 2.2 迁移 0030（`0030_ta73_purge_gate_facts.py`，down_revision="0029"）

- **不改 0029 文件**，不改 0029 建的表、触发器和函数；0030 只**新增两个函数**，不建表、不改列、不动数据。
- 函数放在 `ops`，不放在 `ingest_private`：调用 `ingest_private` 里的函数需要该 schema 的 USAGE，而 T-O57 规定 aia_maint 不得有（grants:179-181）。aia_maint 已有 `ops` 的 USAGE（grants:489-491）。
- `ops.gate_user_refs(p_user uuid) RETURNS TABLE(bindings bigint, scopes bigint)`：SECURITY DEFINER，`SET search_path=pg_catalog`，STABLE，只读计数。scope 的范围是「该用户的绑定引用的 scope」加上「`origin_licence_id` 属于该用户证书的 scope」。给 dry-run 显示行数用。
- `ops.purge_user_gate_facts(p_user uuid) RETURNS TABLE(bindings bigint, scopes bigint)`：SECURITY DEFINER，`SET search_path=pg_catalog`。
  - 前置：`app.users` 中该用户的 `status` 必须是 `purging`，否则抛 `gate_purge_requires_purging_user`。这一步保证它只能在 CLI 的数据状态门事务里生效（CLI:19-22）。
  - 先记下范围内的 scope id，再删该用户的绑定，再删这些 scope。
  - 如果某个 scope 仍被**其他用户**的绑定引用，就抛 `gate_scope_shared` 并整笔回滚，不做部分删除。外键 `bindings.scope_id → scopes.id`（0029:22）没有级联，这里也是第二道保险。
  - 返回删除行数，CLI 写进审计 `admin.user_data_deleted` 的行数里。
- 两个函数都 `REVOKE ALL ... FROM PUBLIC`；`aia_maint` 存在时 `GRANT EXECUTE ... TO aia_maint`；不授 aia_api、aia_ingest。
- **downgrade**：只 `DROP FUNCTION` 这两个函数。没有数据可丢，可无条件执行；0030→0029→0030 往返结构一致。
- **数据**：upgrade 和 downgrade 都不删、不改任何行。只有用户删除 CLI 在 purging 事务里调用 purge 函数时才删行，这是 plan 7.3 规定的物理删除，不是迁移行为。删光后 0029 的降级守卫（0029:85-92）照常按「是否还有行」判断，不受影响。
- **锁和事务**：`CREATE FUNCTION` 和 `DROP FUNCTION` 只锁函数对象本身，不取任何表锁，不重写表。整个迁移在 alembic 的单事务里，毫秒级完成。部署仍按第 9 条「先停进程、备份，再迁移」执行。
- **purge 运行时的锁**：在 CLI 事务里对该用户的绑定行和 scope 行取行锁。删除证书行时 0029 触发器还会跑一次全表 prune（0029:65），会和并发的证书 UPDATE 互等（M3 的已知行为）。CLI 本来就是停机维护时人工执行，可以接受。

## 3. M3 锁争用复现记录（只记录，不设计）

隔离 PG 中，会话 A 在事务里更新证书 1 的 `status` 并保持 3 秒，会话 B 更新**另一张**证书 2 的 `status`：B 在 `lock_timeout=500ms` 下失败，报错位置是 prune 里的 `DELETE FROM ingest_private.mairui_gate_bindings`（0029:40）；不设超时时 B 一直等到 A 提交。结论：争用确实存在。但主线的证书行写入点只有 api 的人工操作（见 §0），事务都很短，所以判不必要。**重新评估条件**：吸收门控应用代码（T-B99 基座，ingest 在每个事务里调 prune），或者 ingest 开始写证书行。到那时 M2 和 M3 一起做。

## 4. M5 搁置说明（需另一个模型复核）

- 0029:57-63 的 CASE 问题属实，已复现：ip_limited 且 `paused_until=删除后 120 秒` 时，`expires_at - deleted_at = 00:02:00`。
- 但主线没有读取绑定的代码，所以单独发 0030 改 CASE，对「1 小时内 3 次 → 暂停 1 小时」（docs/plan.md:406）没有任何作用。
- **新发现，主线上已经存在的绕过路径（与 0029 无关）**：升级计数 `ip_limited_hits` 只在 ingest 内存里，按证书 id 保存（`ingest/state.py:66、149-155`，`ingest/core.py:68-73`）。删除再添加同一证书会生成新行、新 id，冷却记录只恢复 `status` 和 `paused_until`（`licences/service.py:373-385`），计数清零；ingest 重启也会清零。修这个问题要改应用代码，不属于 0030。
- 判定：搁置，等吸收门控应用代码时与它一起设计，届时由另一个模型复核升级规则和绑定保留期。主线这条绕过的影响是：单用户部署里只有用户本人能删除再添加证书。是否单独立项，交给编排者和用户决定。
